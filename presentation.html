Sagard Technical Case Study

Portfolio Metrics Extraction

Turning a folder of inconsistently formatted portfolio-company PDFs into one reviewable table — and what it would take to run this every day, for real.

Prepared by Chanakyan Pooventhan Repo chanakyan04/sagardcasestudy Scope crawl-phase proof of concept
The problem

Every portfolio company reports differently — on purpose or not.

Sagard receives quarterly reporting packages as PDFs. Each company structures and labels its own metrics: one calls it “Net Revenue Retention,” another “Net Dollar Retention,” a third “Net Pound Retention.” One company renamed itself mid-series. One lender relabeled the same metric three different ways across five quarters. Comparing performance across companies, or over time, currently means a person reading every PDF by hand.

24 sample reports

9 portfolio companies, spanning Q2 2024 – Q2 2025, plus one multi-company roll-up document.

No shared schema

Financial metrics, operating metrics, and prose commentary, mixed freely, named however each company likes.

Approach

A deterministic reader, not a model.

The reports are text-based PDFs, not scans — so this isn't an OCR problem. And an LLM-based extractor would generalize better to metrics I didn't anticipate, but trades away reproducibility, speed, and an API-key dependency for a 1–2 hour crawl pass. I chose a regex/alias-based extractor instead: fully deterministic, easy to audit line-by-line, and a natural first pass to layer an LLM on top of later, for exactly the cases it fails.

  • Read pdfplumber pulls raw text per page, joined into one document.
  • Match each of 8 target metrics has an ordered list of known label phrasings; most-specific alias wins first.
  • Parse the matched value token ($12.7M, (0.55M), 148bps) becomes a number + unit.
  • Fall back headcount, sometimes disclosed only in prose, gets a narrative-text regex as a second pass.

What we built — judgment calls

Where the ambiguity actually lived.

Company renames

FleetLink → Apex Freight is one company, confirmed by its own footnote. Mapped by hand, not auto-detected — inferring identity across a name change from text alone is a false-positive-prone problem on its own.

Relabeled metrics

LendBridge renames the same metric three ways across five quarters. Treated as equivalent only where the reports' own footnotes confirm it, not just similar wording.

Similar ≠ same

"Net Charge-off Rate" is a credit-loss metric, not customer churn, even though it sits in a churn-shaped table row. Left unmapped, on purpose.

Multi-company doc

One file rolls up four companies in a different layout. Detected and explicitly skipped — flagged in the console output, not silently dropped.

Where this goes next

Crawl, walk, run.

What's built is the crawl phase: point it at a folder, get a table back. The real question is what changes when these PDFs don't sit in a folder — they arrive every night, forever, and the output has to land somewhere the rest of the firm can query it.

Crawl
a folder in, a CSV out — built today
Walk
daily ingestion, human review, a warehouse
Run
dashboards, alerting, portfolio-wide trend analysis

Real-world path — concept

What changes once it runs every day.

  • Idempotency a re-run or a re-sent PDF must not double-write a company-period row.
  • Schema versioning the metric taxonomy will grow; RAW must survive it, CURATED must migrate deliberately.
  • Identity over time company renames need an explicit mapping table (SCD Type 2), not a hard-coded dict.
  • Audit trail keep the raw source line for every value, the way metrics_long.csv already does — non-negotiable for a PE firm's numbers.
  • Monitoring alert when a company's coverage % drops quarter-over-quarter — that's a format change, not a metric absence.
  • Access control portfolio financials in a shared warehouse need row/column-level permissions per fund or deal team.

This is a design conversation, not a build — happy to go deeper on any piece of it.
